# WebMessenger 웹 메신저 개발 작업계획서
**버전:** 1.0  
**개발 환경:** Windows PC / ChatGPT Codex  
**개발 목표:** 다중 사용자가 실시간으로 대화하는 웹 메신저  
**배포 우선순위:** ChatGPT Sites → 필요 시 대체 호스팅  
**프로젝트 상태:** 신규 개발 계획

---

## 1. 프로젝트 목표

카카오톡·텔레그램·디스코드 등 일반 메신저의 기본 기능을 제공하는 웹 기반 메신저를 개발한다.

개발 기본 원칙은 다음과 같다.

1. 현재 Windows PC에서 Codex를 통해 개발한다.
2. 웹브라우저에서 별도 프로그램 설치 없이 사용할 수 있어야 한다.
3. Windows·macOS·Android·iOS를 지원한다.
4. 여러 사용자가 각자의 계정으로 동시에 접속할 수 있어야 한다.
5. 사용자 간 대화 내용은 서버에 저장되고 다른 기기에서 다시 로그인해도 유지되어야 한다.
6. 모바일과 데스크톱 화면에 최적화한다.
7. ChatGPT Sites를 우선 배포 환경으로 검토한다.
8. 전체 소스코드는 GitHub에 별도로 관리하여 다른 PC에서 개발을 계속할 수 있게 한다.
9. 새로운 기능을 추가해도 기존 대화 기록과 사용자 데이터가 보존되도록 설계한다.

초기에는 소규모 초대형 베타 서비스로 운영하고, 검증 후 일반 사용자에게 공개하는 것을 목표로 한다.

## 2. 주요 기능 명세

### 2.1 사용자 계정

- 이메일 기반 회원가입 및 로그인
- 이메일 인증과 계정 복구
- 고유 사용자 ID 설정 및 중복 확인
- 닉네임·프로필 사진·상태 메시지
- 프로필 수정
- 여러 기기에서 로그인
- 로그아웃 및 계정 탈퇴
- 다른 사용자의 검색 허용 여부 설정

사용자 ID는 `@username` 형식으로 표시한다. 실제 내부 계정 식별에는 변경되지 않는 UUID를 사용한다.

ChatGPT 계정이 없는 일반 사용자도 가입할 수 있도록 자체 회원 인증 체계를 설계한다. 인증 구현은 검증된 외부 인증 서비스 또는 Sites에서 지원하는 안전한 방식을 이용하고, 비밀번호·토큰 체계를 임의로 직접 구현하지 않는다.

### 2.2 친구 검색 및 관리

친구 검색은 다음 방식을 지원한다.

- 사용자 ID로 정확히 검색
- 닉네임 검색(공개를 허용한 사용자만)
- 친구 초대 링크
- QR코드 친구 추가(후속 단계)

친구 관계는 다음 상태를 구분한다.

- 친구 아님
- 친구 요청 보냄
- 친구 요청 받음
- 친구
- 차단됨

친구 관리에는 친구 요청 수락·거절·취소, 친구 삭제, 차단·해제, 친구 목록 검색 및 정렬 기능을 포함한다.

동일한 친구 요청이 중복 생성되지 않도록 하며, 차단된 사용자의 접근과 요청을 서버에서 제한한다.

### 2.3 1:1 채팅

- 친구 선택 후 대화 시작
- 텍스트 메시지 실시간 송수신
- 전송 시각 표시
- 읽음·안 읽음 상태
- 메시지 수정·삭제
- 대화 기록 검색
- 이전 대화 불러오기
- 새 메시지 수 표시
- 채팅방 상단 고정
- 알림 끄기
- 대화 목록에서 숨기기

동일한 두 사용자 사이에 1:1 채팅방이 중복 생성되지 않도록 한다.

메시지는 서버 저장이 성공한 후 전송 완료 상태로 처리한다.

### 2.4 그룹 채팅

- 새 그룹 채팅방 만들기
- 그룹명 및 대표 이미지 설정
- 친구 초대
- 참여자 목록
- 관리자 권한
- 그룹 멤버 퇴장·강퇴
- 초대 제한
- 그룹 채팅방 나가기
- 그룹 내 메시지 검색
- 그룹 공지
- 그룹 알림 설정

역할은 방장·관리자·일반 참여자로 구분한다.

방장이 나가면 지정된 관리자에게 권한을 이양하거나 사전에 정의한 규칙을 적용한다.

### 2.5 친구 목록과 채팅방 관리의 분리

친구 관계와 채팅방 참여 관계는 별개의 데이터로 관리한다.

예를 들어 친구를 삭제했다고 해서 과거의 대화 내용까지 자동 삭제해서는 안 된다.

채팅방을 목록에서 숨기는 동작, 방에서 나가는 동작, 메시지를 삭제하는 동작을 구분한다.

그룹 멤버가 나간 뒤 과거 메시지에 접근할 수 있는 범위는 별도 권한 규칙에 따라 처리한다.

### 2.6 파일 전송

지원 목표는 다음과 같다.

- 이미지 및 GIF
- 일반 문서
- PDF
- HWP·HWPX
- DOCX·XLSX·PPTX
- 압축 파일

파일은 안전한 저장소에 보관한다.

초기에는 파일 크기와 형식에 제한을 두고 운영하며, 다운로드 시 채팅방 접근 권한을 확인한다.

이미지 미리보기와 파일 다운로드를 우선 구현하고, PDF·Office 문서의 인라인 미리보기는 후속 기능으로 분리한다.

### 2.7 후속 확장 기능

- PWA 설치
- 새 메시지 웹 푸시 알림
- 메시지 답장·전달·반응
- 음성 메시지
- 음성 및 영상 통화
- 사용자 신고·관리자 제재
- 데이터 내보내기
- AI 챗봇을 그룹 채팅에 초대하는 기능

후속 기능은 초기 버전의 핵심 구조를 변경하지 않고 추가할 수 있도록 설계한다.

## 3. UI/UX 설계

### 3.1 데스크톱

기본 화면은 세 영역으로 구성한다.

**왼쪽 탐색 영역**
- 내 프로필
- 친구
- 채팅
- 알림
- 설정

**중앙 목록 영역**
- 친구 검색·친구 목록
- 채팅방 검색·채팅방 목록
- 최근 메시지
- 읽지 않은 메시지 수
- 채팅방 생성 버튼

**오른쪽 본문 영역**
- 대화 메시지
- 메시지 입력창
- 첨부파일
- 채팅방 상세정보
- 멤버 목록

사이드바 너비는 조정할 수 있도록 하고, 창 크기가 작아지면 자동으로 레이아웃을 축소한다.

### 3.2 모바일

모바일은 화면 전체를 이용하는 단일 패널 중심으로 구현한다.

- 하단 또는 상단 탐색 메뉴
- 친구·채팅 목록에서 대화방으로 진입
- 뒤로 가기로 목록 복귀
- 모바일 키보드가 나타나도 메시지 입력창 유지
- 터치 조작과 긴 메시지에 최적화
- 브라우저 확대·축소와 화면 회전 대응

반응형 웹으로 구현하되 PWA 설치를 위한 기본 구조를 확보한다.

### 3.3 디자인

- 한국어 기본 UI
- 라이트·다크 모드
- 읽기 편한 글꼴
- 대화 말풍선과 날짜 구분선
- 사용자별 아바타
- 모던하고 단정한 디자인
- 키보드 탐색·접근성 고려

디자인은 카카오톡·디스코드·슬랙의 장점을 참고하되 독자적인 UI로 개발한다.

## 4. 기술 아키텍처

### 4.1 기술 선정 원칙

프런트엔드의 기본 개발 언어는 TypeScript로 한다.

React 기반 UI를 우선 검토하고, 상태 관리·라우팅·컴포넌트 구성을 모듈화한다.

백엔드는 ChatGPT Sites에서 실제 지원되는 기술을 우선 활용하되, 서비스 운영에 필수적인 기능이 부족하면 외부 백엔드를 검토한다.

**우선 검토 구조**

- 프런트엔드: React + TypeScript
- 스타일: Tailwind CSS 또는 동등한 방식
- 서버: Sites 지원 런타임
- 데이터베이스: Sites D1
- 파일 저장: Sites R2
- 실시간 전송: Sites 지원 WebSocket 기반 구조
- 버전 관리: Git + GitHub
- 테스트: Vitest + Playwright 등 검증된 도구

단, 특정 프레임워크나 서버 라이브러리가 Sites 런타임에서 정상 작동한다고 미리 가정하지 않는다.

### 4.2 실시간 채팅의 필수 처리 방식

메시지 처리 순서는 다음과 같다.

1. 클라이언트가 메시지를 전송한다.
2. 서버가 로그인 상태와 채팅방 참여 권한을 검사한다.
3. 서버가 중복 요청을 검사한다.
4. 메시지를 데이터베이스에 저장한다.
5. 저장 성공 응답을 발신자에게 전송한다.
6. 수신자에게 실시간 메시지 이벤트를 전달한다.
7. 접속이 끊겼다가 다시 연결되면 누락된 메시지를 조회한다.

메시지마다 고유 ID와 생성 시간을 저장하고, 서버 기준의 정렬 순서를 보장한다.

네트워크 재시도로 인해 같은 메시지가 두 번 표시되지 않도록 중복 방지 키를 사용한다.

실시간 연결이 끊겨도 이미 저장된 메시지는 사라지지 않아야 한다.

### 4.3 Sites 실시간 기능의 선행 검증

본격적인 기능 개발 전에 별도의 최소 실험을 진행한다.

- 두 개의 독립 사용자 세션 연결
- WebSocket 연결 가능 여부
- A 사용자가 보낸 메시지가 B 사용자에게 전달되는지 확인
- 데이터베이스 저장 확인
- 페이지 새로고침 후 기록 유지
- 연결 종료 및 재접속 테스트
- 게시된 Sites URL에서도 동일하게 동작하는지 확인

WebSocket 연결 자체가 가능한 것과 다중 채팅방의 동시 접속 상태를 안정적으로 유지하는 것은 다르므로 각각 검증한다.

Sites 환경만으로 요구 성능이나 지속성을 확보하기 어렵다면 외부 실시간 백엔드(Supabase·Convex 등)를 대안으로 검토한다.

이 경우 프런트엔드를 재작성하지 않도록 백엔드 접근 인터페이스를 분리한다.

### 4.4 데이터 모델

최소한 다음 데이터 엔터티가 필요하다.

| 테이블 | 주요 내용 |
|---|---|
| users / profiles | 계정 ID, 사용자 ID, 닉네임, 프로필 |
| friend_requests | 친구 요청 발신자, 수신자, 상태 |
| friendships | 수락된 친구 관계 |
| blocks | 차단 관계 |
| chat_rooms | 채팅방 유형, 이름, 생성자 |
| chat_members | 채팅방 참여자, 역할, 입장·퇴장 상태 |
| messages | 메시지 ID, 발신자, 채팅방, 내용, 시각 |
| read_states | 사용자별 마지막 읽은 메시지 |
| attachments | 첨부파일 경로, 크기, 소유권 |
| invitations | 초대 링크, 만료일, 사용 조건 |
| reports | 신고 및 관리자 처리 기록 |

모든 사용자 ID는 변경 가능한 닉네임과 분리한다.

친구 관계와 1:1 채팅방에는 중복 방지 제약을 적용한다.

메시지 조회는 페이지 단위로 처리하여 대화 기록이 많아져도 성능이 저하되지 않게 한다.

데이터베이스 스키마 변경은 버전별 마이그레이션 파일로 관리한다.

## 5. 보안·개인정보 보호

다음 사항을 초기 설계부터 의무적으로 반영한다.

- HTTPS 통신
- 인증되지 않은 사용자 접근 차단
- 모든 데이터 조회·변경의 서버 측 권한 검사
- 채팅방 비참여자의 메시지 열람 차단
- 첨부파일 다운로드 권한 확인
- 사용자 입력 XSS 방어
- 데이터베이스 쿼리의 안전한 매개변수 처리
- 세션 및 토큰 보안
- 로그인·친구 검색·메시지 전송 횟수 제한
- 초대 링크 만료 및 무효화
- 신고·차단 기능
- 최소한의 개인정보 수집
- 개인정보 처리방침과 탈퇴·삭제 절차 마련

서비스 운영자가 대화 내용을 기술적으로 열람할 수 있는 구조인지 명확하게 설명해야 한다.

종단간 암호화(E2EE)는 초기 구현 범위에 포함하지 않으며, 구현하지 않은 상태에서 E2EE를 지원한다고 표시하지 않는다.

공개 서비스를 시작하기 전에 개인정보 보호 및 서비스 운영에 필요한 법적 요건도 별도로 점검한다.

GitHub에는 신규 비공개 저장소 `web-messenger`를 사용하는 것을 기본안으로 한다.

기존에 개발하던 다른 프로젝트의 저장소나 로컬 파일을 임의로 수정·삭제하지 않는다.

각 단계가 끝나면 변경 사항과 테스트 결과를 기록하고, 검증된 코드에 대해 Git 커밋을 생성한다.

GitHub 원격 저장소 업로드와 서비스 배포는 사용자 승인 후 수행한다.

## 7. 단계별 개발 계획

### 0단계 — 개발 환경 및 기술 검증

**목표:** 현재 Windows PC에서 개발 가능한 환경을 확인한다.

작업 내용:

- Codex의 로컬 프로젝트 접근 확인
- Git·Node.js·패키지 관리자 상태 점검
- GitHub 인증 및 저장소 연결 가능 여부 점검
- ChatGPT Sites 접근 여부 확인
- Sites 런타임·데이터베이스·WebSocket 지원 검증
- 자체 로그인 구현 가능 방식 검토
- 개발·테스트·배포 구성을 최종 결정

**완료 기준:** 기술 검증 결과, 제약사항, 채택 기술과 대안이 문서화되어야 한다.

### 1단계 — 기본 UI와 계정 관리

- 반응형 기본 화면
- 로그인 및 회원가입
- 사용자 프로필
- 고유 ID 설정
- 사용자 검색
- 기본 환경설정 화면

**완료 기준:** 서로 다른 테스트 계정 2개로 로그인하고 사용자 검색이 가능해야 한다.

### 2단계 — 친구 관리

- 친구 요청
- 수락·거절·취소
- 친구 목록
- 친구 삭제
- 차단·차단 해제
- 검색 공개 범위 설정

**완료 기준:** 두 계정 간 친구 관계 변경이 양쪽 화면과 데이터베이스에 일관되게 반영되어야 한다.

### 3단계 — 1:1 실시간 채팅

- 채팅방 생성
- 메시지 전송 및 수신
- 대화 기록 저장
- 재접속 시 메시지 복구
- 읽지 않은 메시지
- 채팅방 목록

**완료 기준:** 서로 다른 브라우저와 기기에서 실제 메시지를 주고받고 기록을 복구할 수 있어야 한다.

### 4단계 — 그룹 채팅

- 그룹 생성
- 멤버 초대
- 방장·관리자 기능
- 그룹 설정
- 멤버 나가기·강퇴
- 그룹 채팅 기록

**완료 기준:** 최소 3개 테스트 계정에서 그룹 대화를 검증해야 한다.

### 5단계 — 파일·사용성 개선

- 이미지·파일 업로드 및 다운로드
- 이미지 미리보기
- 메시지 수정·삭제
- 메시지 검색
- 알림 설정
- PWA 설치 기능 검토 및 적용

**완료 기준:** 권한이 있는 사용자만 파일을 열 수 있고 모바일에서도 주요 기능을 이용할 수 있어야 한다.

### 6단계 — 베타 서비스

- 보안 점검
- 브라우저·모바일 호환성 테스트
- 여러 사용자 동시 접속 테스트
- 백업 및 복원 절차 검증
- 관리자 기능 최소 구현
- 실제 사용자 피드백 수집
- 검증 후 공개 범위 확대

**완료 기준:** 주요 보안 및 데이터 손실 문제가 해결되고 사용자 승인 하에 외부 공개가 가능해야 한다.

## 8. 필수 테스트 시나리오

아래는 초기 필수 테스트다.

| 시나리오 | 기대 결과 |
|---|---|
| A가 B를 검색 | B의 공개 프로필 표시 |
| A가 친구 요청 | B에게 요청 표시 |
| B가 수락 | 양쪽 친구 목록 반영 |
| A가 B에게 메시지 전송 | B에게 실시간 표시 |
| B가 오프라인인 동안 메시지 전송 | 재접속 후 메시지 확인 |
| 동일 메시지 재전송 | 중복 저장·표시 방지 |
| A·B·C 그룹 생성 | 세 사용자가 동일 대화 확인 |
| 비참여자가 채팅방 API 호출 | 서버에서 접근 거부 |
| 차단 사용자가 친구 요청 | 요청 차단 |
| 권한 없는 사용자의 첨부파일 접근 | 다운로드 거부 |
| 다른 PC에서 로그인 | 허용된 대화 기록 복원 |

자동화 가능한 테스트는 코드로 작성한다.

화면만으로 성공 여부를 판단하지 말고 서버 저장, 권한 검사, 재접속 결과까지 확인한다.

## 9. Codex 운영 규칙

### 역할

Codex는 구현 담당 개발 에이전트이자 기술 검증 담당이다.

사용자는 개발 우선순위, 외부 서비스 사용, 비용 발생, 공개 배포 등의 최종 승인자다.

### 실행 시작 조건

사용자가 명시적으로 개발 착수를 지시한 후에만 작업을 실행한다.

계획 검토 요청은 파일 수정·계정 생성·원격 업로드·서비스 배포를 허가한 것으로 해석하지 않는다.

### 실행 범위

승인된 프로젝트 폴더에서 개발하고, 필요한 라이브러리를 설치하며, 테스트를 수행할 수 있다.

외부 유료 서비스 가입, 결제, 기존 프로젝트 삭제, 운영 데이터 삭제, 공개 배포, 비밀정보 전송 등은 별도 승인을 받는다.

다른 대화나 Codex 세션의 내용을 자동으로 알고 있다고 가정하지 않는다.

### 개발 진행 방식

- 작업을 단계와 세부 태스크로 분리한다.
- 선행 작업이 끝나지 않은 기능은 무리하게 병렬 진행하지 않는다.
- 독립적인 UI·테스트·문서 작업은 필요할 때 분담할 수 있다.
- 단계 종료 시 실제 테스트 결과를 남긴다.
- 오류가 발생하면 원인과 재현 방법을 기록한다.
- 사용자가 명시하지 않은 기능을 임의로 확대하지 않는다.
- 중요 설계 변경은 `DECISIONS.md`에 기록한다.
- 작업 진행 상황은 `STATUS.md`에 갱신한다.

### 보고 형식

매 단계 종료 시 다음 형식으로 보고한다.

1. **완료한 작업**
2. **수정·생성한 파일**
3. **실행한 테스트와 결과**
4. **미완료 및 발견된 문제**
5. **Git 커밋 정보 및 원격 반영 여부**
6. **다음 단계 작업**
7. **사용자 승인 필요 사항**

완료 여부는 실제 실행·검증 결과에 근거하여 보고한다.

## 10. 배포 및 다른 PC 연속 개발

개발 소스는 GitHub를 기준으로 버전 관리한다.

다른 PC에서는 같은 저장소를 복제하거나 최신 커밋을 가져와 개발을 이어갈 수 있도록 한다.

다음 사항을 구분한다.

- GitHub: 프로그램 소스코드
- Sites 또는 다른 호스팅: 실제 메신저 웹사이트
- 데이터베이스: 사용자·친구·채팅 기록
- 파일 저장소: 첨부파일
- Codex 작업 기록: 개발 과정 및 작업 지시

소스코드 동기화와 데이터베이스 동기화는 별개다.

ChatGPT Sites를 최종 배포 대상으로 사용할 경우 Codex에서 Sites 생성·업데이트 절차를 검증한다. GitHub 커밋이 Sites에 자동 배포되는지는 실제 지원 방식이 확인되기 전까지 가정하지 않는다.

데이터베이스와 첨부파일은 정기적으로 내보내고 복원 가능한 형태의 백업 구조를 마련한다.

## 11. 초기 개발 성공 기준

초기 MVP의 완성 조건은 다음과 같다.

- 서로 다른 두 사용자가 가입할 수 있다.
- 사용자 ID로 상대방을 찾을 수 있다.
- 친구 요청과 수락이 가능하다.
- 1:1 메시지를 실시간으로 주고받는다.
- 메시지 기록이 보존된다.
- 다른 PC나 휴대폰에서 로그인해 대화를 이어갈 수 있다.
- 그룹 채팅을 만들 수 있다.
- 접근 권한을 서버에서 검사한다.
- 모바일에서도 정상 이용할 수 있다.
- 소스코드와 개발 문서가 GitHub로 이전 가능한 상태다.

이 조건을 만족하지 않는 단순 채팅 화면이나 임시 시뮬레이션은 MVP 완료로 인정하지 않는다.

## 12. 첫 번째 Codex 작업 지시

이 계획서를 받은 Codex는 우선 **0단계 환경·기술 검증 및 프로젝트 초기화**에 착수한다.

첫 작업에서는 다음을 수행한다.

1. 현재 Windows 개발 환경을 확인한다.
2. 신규 프로젝트 폴더를 준비한다.
3. 기존 프로젝트와 충돌하지 않는지 확인한다.
4. ChatGPT Sites 개발·배포 지원 범위를 검증한다.
5. 실시간 통신과 저장 방식을 비교한다.
6. 기술 스택을 결정한다.
7. 기본 프로젝트 구조와 개발 문서를 생성한다.
8. 최소 실행 가능한 화면을 만들고 로컬 구동을 확인한다.
9. 다음 단계에 필요한 작업 목록을 정리한다.

**첫 단계에서는 공개 배포와 유료 서비스 가입을 수행하지 않는다.**

완료 후 채택한 기술 구조, 실행 가능한 결과물, 실제 테스트 결과, 해결되지 않은 제약을 보고한다.

---

**최종 개발 원칙**

기능의 개수보다 실제 동작, 데이터 안정성, 보안, 향후 유지보수 가능성을 우선한다.

ChatGPT Sites를 우선 활용하되, 기술적 제약이 발견되면 검증된 대안을 제시하고 사용자의 승인 후 적용한다.

프로젝트를 여러 PC에서 이어서 개발할 수 있도록 코드·기술 결정·테스트·진행 상황을 지속적으로 기록한다.
